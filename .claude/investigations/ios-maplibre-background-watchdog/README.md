# iOS: зависание/перезагрузка устройства — MapLibre deadlock на уходе в background

**Статус: не починено, воспроизведено трижды на реальном устройстве.
Механизм установлен (разбор 2026-09-01, см. одноимённый раздел внизу):
главный поток синхронно и без таймаута ждёт подтверждения от потока
`org.maplibre.mbgl.OnlineFileSource` внутри
`-[MLNOfflineStorage pauseFileSource:]`; сам этот поток в момент зависания
простаивает — он просто не получает CPU, потому что два потока приложения с
`QOS_CLASS_USER_INTERACTIVE` держат оба ядра двухъядерного iPhone SE.
Апстрим-баг известен и не починен: maplibre/maplibre-native#2328.**

Коротко для `ui/map/CLAUDE.md` — там же короткая версия этой находки в
разделе «Грабли». Этот файл — полная фактура для следующей сессии: как
добыты доказательства, что именно в них есть, что уже исключено, что делать
дальше.

## Симптом (со слов пользователя)

Приложение зависло, экран стал чёрным, вероятна перезагрузка телефона.
Устройство — iPhone 8,4 (SE 2016/подобный форм-фактор по `modelCode`), iOS
15.8.8 (19H422), подключено к Mac по кабелю.

## Инцидент №1 — 2026-08-17, 20:07:05–25 (уже был задокументирован раньше)

Есть полноценный crash-репорт самого приложения:
`leshy-2026-08-17-200725.ips` (копия лежит рядом с этим файлом,
`./leshy-2026-08-17-200725.ips`).

Ключевые поля:

```json
"exception": {"type": "EXC_CRASH", "signal": "SIGKILL"}
"termination": {
  "namespace": "FRONTBOARD",
  "reasons": [
    "<RBSTerminateContext| domain:10 code:0x8BADF00D explanation:[application<compose.project.leshy.leshy>:19695] failed to terminate gracefully after 5.0s",
    "WatchdogEvent: process-exit",
    "WatchdogCPUStatistics: (",
    "\"Elapsed total CPU time (seconds): 79.780 (user 79.780, system 0.000), 100% CPU\",",
    "\"Elapsed application CPU time (seconds): 68.155, 85% CPU\""
  ]
}
```

`0x8BADF00D` — стандартный код Apple watchdog «приложение не ответило
вовремя». Здесь конкретно: не уложилось в 5 секунд на завершение
(`applicationDidEnterBackground` → OS ждёт, что процесс освободит ресурсы и
уйдёт в background корректно), при этом всё это время жрало ~100% CPU.

Стек главного потока (`threads[0]`, `queue: com.apple.main-thread`),
сверху вниз от места, где реально завис:

```
UIApplication _applicationDidEnterBackground
  -[_UISceneLifecycleMultiplexer ...] (обычная цепочка UIKit scene lifecycle)
  __47-[UIApplication _applicationDidEnterBackground]_block_invoke
  -[NSNotificationCenter postNotificationName:object:userInfo:]
  _CFXNotificationPost / _CFXRegistrationPost / __CFNOTIFICATIONCENTER_IS_CALLING_OUT_TO_AN_OBSERVER__
  → 2 кадра БЕЗ символов, imageIndex=3   ← это MapLibre.framework
  std::__1::future<void>::get()
  std::__1::__assoc_sub_state::copy()
  std::__1::__assoc_sub_state::__sub_wait(...)
  std::__1::condition_variable::wait(...)
  _pthread_cond_wait$VARIANT$mp
  __psynch_cvwait
```

`usedImages[3]` в этом же файле:

```json
{"name": "MapLibre", "path": "/private/var/containers/.../leshy.app/Frameworks/MapLibre.framework/MapLibre"}
```

Т.е. **главный поток поймал `UIApplicationDidEnterBackgroundNotification`,
это дошло до наблюдателя внутри `MapLibre.framework` (два кадра без
символов — релизный бинарь, приватные символы стрипнуты), и там код
СИНХРОННО заблокировался на `std::future<void>::get()`** — ждёт результата,
который должен был прийти с другого потока/из другой задачи планировщика
mbgl (C++ ядро MapLibre), и не дождался за отведённое время.

## Инцидент №2 — 2026-08-22, 09:45:23–27 (это сегодняшнее зависание)

В этот раз **отдельного crash-репорта `leshy` нет** — система была
настолько заморожена, что даже `ReportCrash` не успел отработать до того,
как watchdog перезагрузил устройство целиком. Но есть косвенное, всё равно
достаточно прямое доказательство: watchdog сгенерировал репорты для ПЯТИ
системных демонов одновременно —

```
logd-2026-08-22-094524.ips / 094526.ips
mediaserverd-2026-08-22-094523.ips / 094525.0002.ips
runningboardd-2026-08-22-094525.ips / 094527.ips
thermalmonitord-2026-08-22-094524.000.ips / 094526.000.ips
wifid-2026-08-22-094525.000.ips / 094527.000.ips
```

У каждого `termination` вида:

```json
{"namespace": "WATCHDOG", "indicator": "monitoring timed out for service",
 "details": ["(5 monitored services unresponsive): checkin with service: <name> failed to send ping message, ... hung 60 seconds since last successful checkin"]}
```

Это фингерпринт **полносистемной** перезагрузки по watchdog (не убийства
одного приложения) — ядро/шедулер были застопорены настолько, что даже
логирование, медиасервер, менеджер процессов, термомонитор и wifi-демон не
могли ответить на пинг 60 секунд подряд.

Panics-папка (`idevicecrashreport` тоже её вытаскивает) была пуста — то
есть классического kernel panic со строкой паники здесь не было, это именно
watchdog-таймаут на уровне userspace-мониторинга.

Каждый из этих `.ips`-файлов несёт встроенный **полный стекшот всех
процессов системы** на момент зависания (`body["stackshot"]`, структура
`{processByPid: {<pid>: {...}}, binaryImages: [...]}`, ключ процесса —
`procname`, не `procName`). В `processByPid` нашёлся процесс `leshy`:

```
pid 5377, procname "leshy"
residentMemoryBytes ≈ 194 МБ
userTimeTask ≈ 112.69 сек
```

Из 38 потоков процесса — два не связанных друг с другом потока с
`qosEffective: QOS_CLASS_USER_INTERACTIVE` и `state: TH_RUN`, на которые
пришлось **~106 из 112 секунд** всего CPU-времени процесса:

```
thread 219009: userTime ≈ 56.94s, TH_RUN, QOS_CLASS_USER_INTERACTIVE
thread 219576: userTime ≈ 49.34s, TH_RUN, QOS_CLASS_USER_INTERACTIVE
```

Все `org.maplibre.mbgl.*`-потоки (Worker 1..4, DatabaseFileSource,
OnlineFileSource, ResourceLoaderThread и т.д.) в этот момент были в
`TH_WAIT` — то есть простаивали, ждали чего-то, а не сами жрали CPU. Это
согласуется с картиной из инцидента №1: где-то (скорее всего, главный/
UI-поток) заблокировано ожидание, которое never resolves, пока остальной
пул MapLibre бездействует.

**Формат стекшота в этих daemon-репортах компактнее, чем в app-репорте** —
`binaryImages` тут не даёт путь/имя файла (только UUID + база + флаг вроде
`"S"`/`"U"`/`"A"`), так что напрямую сопоставить оффсеты этих двух
"горячих" потоков с конкретным бинарём (MapLibre или нет) в этом формате не
вышло за разумное время. Это единственный пробел по сравнению с инцидентом
№1 — но общая картина (главный/высокоприоритетный поток жрёт под 100% CPU
почти всё время жизни процесса, воркеры MapLibre простаивают) настолько
совпадает с задокументированным инцидентом №1, что считаю это тем же самым
багом, просто без собственного crash-репорта на этот раз.

## Итоговый вывод

Один и тот же баг воспроизвёлся дважды за 5 дней на одном устройстве:
**главный поток блокируется внутри `MapLibre.framework` синхронным
ожиданием (`std::future::get()`/condition variable) при переходе приложения
в background**, если попасть в неудачный момент (что именно делает
MapLibre фоном в этот момент — не установлено; см. гипотезы ниже). Раньше
это характеризовалось как «воспроизводится редко» — по факту за 5 дней
пользователь поймал его дважды, так что «редко» стоит пересмотреть в
сторону «легко словить, если активно пользоваться картой и сворачивать
приложение».

- **Инцидент №17.08 закончился быстрее** — за 5 секунд не завершившийся
  процесс просто убит (`SIGKILL`), само приложение исчезает, устройство не
  трогает.
- **Инцидент №22.08 тяжелее** — зависание было настолько долгим/полным
  (либо главный поток держал какую-то системную блокировку, либо просто
  весь scheduler был перегружен теми же двумя потоками так, что не осталось
  времени на системные демоны), что это утащило за собой ping-мониторинг
  пяти системных демонов и потребовало полной перезагрузки устройства —
  отсюда чёрный экран и ребут, которые видел пользователь.

## Что НЕ подтверждено (гипотезы, не факты) — писалось до разбора 2026-09-01

> разбором 2026-09-01 (см. самый низ файла): гипотеза про сеть больше не
> нужна, дедлок внутри рендера/Actor-паттерна не подтвердился.

Более раннее (уже существовавшее до этой сессии) описание в
`ui/map/CLAUDE.md` предполагало триггер «сеть внезапно полностью пропала,
пока грузился тайл» — это правдоподобная гипотеза (объясняет, почему
операция «должна быть быстрой, но зависает» — ждёт сетевого таймаута), но
она НЕ подтверждена логами напрямую ни в одном из двух инцидентов: в
crash-репорте нет сведений о состоянии сети в момент краша, а
`idevicediagnostics`/`ideviceinfo` в этой сессии проверялись уже ПОСЛЕ
перезагрузки, не в момент зависания. Считать эту гипотезу одной из
возможных, не единственной.

Другие непроверенные гипотезы:
- Deadlock не про сеть вообще, а про паузу/тardown GL-рендера
  (`mbgl::Scheduler`/Actor pattern) при уходе в фон — реализация MapLibire
  синхронно ждёт, что рендер-поток обработает какую-то задачу, а тот сам
  чего-то ждёт (например, главного потока — классический взаимный deadlock).
- Триггер может быть НЕ специфичен для конкретного экрана — неизвестно,
  был ли в момент любого из двух инцидентов открыт именно экран с картой
  (Запись/Карта/Архив) или что-то другое. Не спрошено/не залогировано.

## Диагностический инструментарий (чтобы не собирать заново в следующий раз)

На Mac уже стоит `libimobiledevice` (`brew install libimobiledevice` даёт
`idevice_id`, `ideviceinfo`, `idevicecrashreport`, `idevicesyslog`,
`idevicediagnostics`).

```bash
# UDID подключённого по кабелю устройства (формат libimobiledevice,
# ОТЛИЧАЕТСЯ от UUID, который показывает `xcrun xctrace list devices`)
idevice_id -l

# базовая информация об устройстве
ideviceinfo -u <UDID>

# ГЛАВНАЯ команда: стягивает и УДАЛЯЕТ (!) с телефона все .ips-репорты
# (крэши приложений, JetsamEvent, Analytics, системные watchdog-репорты,
# содержимое папки Panics) в указанную локальную директорию
idevicecrashreport -u <UDID> -e <путь-назначения>
```

**Важно:** `-e` не просто копирует, а перемещает файлы с устройства — после
этого на телефоне их больше нет. Если нужно повторно проанализировать
именно эти файлы позже, сразу копировать интересующее в постоянное место
(как сделано с `leshy-2026-08-17-200725.ips` в этой же папке) — таблица
`/private/tmp/.../scratchpad` живёт только в рамках одной сессии Claude
Code и не переживёт её закрытие.

### Как читать `.ips`-файл

Файл — не единый JSON: первая строка — компактный JSON-заголовок
(`bundleID`/`timestamp`/`os_version`/`name`/...), после `\n` — второй,
основной JSON-документ (само тело репорта). Пример разбора в Python:

```python
import json
with open('some-report.ips') as f:
    header, body = f.read().split('\n', 1)
header = json.loads(header)
body = json.loads(body)
```

Два разных вида тела встречаются в этом расследовании:

1. **Обычный app-крэш** (`bug_type: "309"`, есть `exception`/`threads`/
   `usedImages`) — `body['threads'][i]['frames']` даёт кадры с `symbol`,
   если он известен (публичные Apple-фреймворки почти всегда
   символизированы; наш `MapLibre.framework` и `Shared.framework` — нет,
   только `imageOffset`/`imageIndex`). `body['usedImages'][idx]` даёт
   `name`/`path` бинаря — так и был опознан индекс 3 как
   `MapLibre.framework` в инциденте №1.
2. **Watchdog-таймаут системного демона** (`termination.namespace ==
   "WATCHDOG"`, `indicator: "monitoring timed out for service"`) — своих
   `threads` не несёт, зато у него есть `body['stackshot']` — снимок
   ВСЕХ процессов системы на момент срабатывания:
   `stackshot['processByPid']` — словарь `{"<pid>": {...}}`, у каждого
   процесса `procname` (нижний регистр!), `residentMemoryBytes`,
   `userTimeTask`, `threadById` (словарь `{"<tid>": {...}}` с `state`
   (`TH_RUN`/`TH_WAIT`/...), `qosEffective`, `userTime` накопительно за
   всё время жизни потока). Это позволяет найти произвольный процесс
   (в т.ч. `leshy`) по имени и увидеть, какие его потоки жрали CPU в
   момент зависания, даже если для НЕГО САМОГО отдельный crash-репорт не
   создался. `stackshot['binaryImages']` в этом формате компактнее (нет
   имени/пути), поэтому сопоставить оффсеты кадров с конкретным бинарём
   тут сложнее, чем в обычном app-крэше.

Фингерпринт полносистемной watchdog-перезагрузки (а не убийства одного
приложения) — фраза **"5 monitored services unresponsive"** /
**"monitoring timed out for service"** в `termination`, повторяющаяся
одновременно в репортах НЕСКОЛЬКИХ разных системных демонов с близкими
таймстемпами.

## Разбор 2026-09-01: механизм установлен

Ниже — что удалось доказать по уже собранным файлам (`leshy-2026-08-17-200725.ips`

### 1. Два безымянных кадра MapLibre из инцидента №1 — расшифрованы

`MapLibre.framework` стрипнут, но ObjC-метаданные в нём остались, а
UUID бинаря из crash-репорта (`16C638E1-97E9-34D0-86BA-C5DA22941CE4`)
**совпадает** с локальной копией
`shared/build/spmKmpPlugin/iosArm64/scratch/arm64-apple-ios/release/MapLibre.framework/MapLibre`
(это префаб из релиза, он одинаков во всех наших сборках). Отсюда:

```bash
otool -oV .../MapLibre.framework/MapLibre   # imp-адреса всех ObjC-методов
```

`imp` `pauseFileSource:` = `0x313a4`, `unpauseFileSource:` = `0x313fc`.
Кадр №7 из инцидента №1 — `imageOffset 201688` = `0x313d8` — попадает
внутрь **`-[MLNOfflineStorage pauseFileSource:] + 52`**. Дизассемблер этого
метода:

```
0x313a4  stp/stp/add/mov          ; пролог
0x313b4  bl   0x57c420            ; self.isPaused
0x313b8  tbz  w0, #0, 0x313c8     ; if (isPaused) return
0x313c8  ldr  x0, [x19, #0x40]    ; _mbglOnlineFileSource
0x313d4  blr  x8                  ; -> pause()        <-- зависли ЗДЕСЬ
0x313d8  ldr  x0, [x19, #0x30]    ; _mbglDatabaseFileSource   (адрес возврата)
0x313e4  blr  x8                  ; -> pause()
```

То есть главный поток стоял на **первом** из двух `pause()` —
на `OnlineFileSource`. Кадр №6 (`0x11acd0`) — заинлайненный
`mbgl::util::Thread<mbgl::OnlineFileSourceThread>::pause()`.

### 2. Это ровно тот же апстрим-баг, что и maplibre/maplibre-native#2328

[Issue #2328 «Offline Storage Crash»](https://github.com/maplibre/maplibre-native/issues/2328)
(открыт 2024-04-24, ноль комментариев, ноль реакции мейнтейнеров, метка `iOS`)
— «крупное продакшн-приложение, воспроизводится только в поле», и в нём
символизированный стек ровно наш:

```
6  MapLibre  mbgl::util::Thread<mbgl::OnlineFileSourceThread>::pause() (thread.hpp:132)
7  MapLibre  -[MLNOfflineStorage pauseFileSource:] (MLNOfflineStorage.mm:86)
```

На `main` (сентябрь 2026) код не изменился ни в `MLNOfflineStorage.mm`, ни в
`thread.hpp`.

### 3. Что именно делает MapLibre на уходе в фон и почему это блокирует

`+[MLNOfflineStorage sharedOfflineStorage]` в своём `dispatch_once`
подписывается на `UIApplicationDidEnterBackgroundNotification` →
`pauseFileSource:` → `OnlineFileSource::pause()` и
`DatabaseFileSource::pause()` (`platform/darwin/src/MLNOfflineStorage.mm`).
Обе уходят в `mbgl::util::Thread<T>::pause()`
(`include/mbgl/util/thread.hpp`):

```cpp
void pause() {
    paused  = std::make_unique<std::promise<void>>();
    resumed = std::make_unique<std::promise<void>>();
    auto pausing = paused->get_future();
    running.wait();
    loop->invoke(RunLoop::Priority::High, [this] {      // задача в чужой ран-луп
        auto resuming = resumed->get_future();
        paused->set_value();
        resuming.get();                                  // поток встаёт до resume()
    });
    pausing.get();      // <-- главный поток. Без таймаута. Навсегда.
}
```

`pausing.get()` — это и есть `std::future<void>::get()` из стека.
**Таймаута нет, отменить нельзя, приоритет не наследуется** (обычный
`std::condition_variable`, а не `os_unfair_lock`/`dispatch_sync`, так что
donation приоритета от главного потока к ждущему не происходит).

Подписка ставится не нами и не опционально: `MLNMapView` при инициализации
дёргает `MLNOfflineStorage.sharedOfflineStorage.databasePath`
(`MLNMapView.mm:718`), так что наблюдатель регистрируется у **любого**
приложения, показавшего карту, даже без офлайн-регионов.

### 4. Почему ожидание не заканчивается — поток-адресат простаивает, а не занят

Ключевой факт, который раньше не был вытащен из инцидента №1: в том же
crash-репорте есть **все 38 потоков**, и поток
`org.maplibre.mbgl.OnlineFileSource` (thread 11) в момент SIGKILL стоял в

```
mach_msg_trap / mach_msg / __CFRunLoopServiceMachPort / __CFRunLoopRun /
CFRunLoopRunSpecific / CFRunLoopRun
```

— то есть **пустой, простаивающий ран-луп**. Он не висел ни в SQLite, ни в
сети, ни в дедлоке. Ему нужно было исполнить микроскопическую задачу
(`paused->set_value()`), и он этого не сделал. Значит, дело не во
внутреннем дедлоке MapLibre, а в том, что поток не получил процессор.

Это подтверждается тем, что видно в стекшотах инцидентов №2 и №3:

- **Устройство двухъядерное** (iPhone8,4 = iPhone SE 1-го поколения, Apple A9).
- Два потока процесса с `QOS_CLASS_USER_INTERACTIVE`, `schedPriority 47`,
  в состоянии `TH_RUN` держат ~90% всего CPU-времени процесса
  (инцидент №3: 70.47с + 41.72с из 123.5с).
- Все `org.maplibre.mbgl.*`-потоки, включая `OnlineFileSource`, —
  `QOS_CLASS_DEFAULT`, `schedPriority 31`, `TH_WAIT`, суммарно единицы
  сотых секунды CPU.

Два непрерывно готовых к исполнению потока приоритета 47 на двух ядрах
не оставляют потоку приоритета 31 ни одного кванта — в разных QoS-полосах
Mach-планировщик не выравнивает их между собой. Отсюда и парадокс
«главный поток ждёт вечно, а тот, кого он ждёт, ничего не делает».

Побочно: попытка MapLibre понизить приоритет этих потоков не работает —
`platform::makeThreadLowPriority()` (`platform/darwin/core/nsthread.mm`)
выставляет `[NSThread currentThread].qualityOfService` уже **после** старта
потока, созданного через `std::thread`, а это по документации Apple no-op.
Отсюда `QOS_CLASS_DEFAULT` в стекшоте вместо ожидаемого `UTILITY`. На
наш случай это влияет мало (31 всё равно ниже 47), но объясняет цифры.

### 5. Первопричина — наша, а не MapLibre: два потока приложения жгут CPU

Инцидент №1: watchdog отчитался `79.780с user, 100% CPU`. Инциденты №2 и №3:
те же два `USER_INTERACTIVE`-потока в `TH_RUN`. В инциденте №3 у процесса
`flags: ["foreground"]` и `timesThrottled: 0`, а в `waitInfo` стекшота есть
строка

```
thread 302093: unfair lock 0x1f53f8980 owned by thread 302356
```

— то есть один из этих двух горячих потоков (302356) ещё и держал
общесистемный `os_unfair_lock`, на котором стоял третий поток.

Разбор кадров этих двух потоков (индексы образов сопоставлены с
`usedImages` инцидента №1 по UUID: `16c638e1…` = MapLibre,
`8ab98b19…` = libdispatch, `16c8ea1a…` = dyld, образ №2 = dyld shared cache,
образ №276 = `leshy.debug.dylib`):

- **thread 301901 — главный поток**: `main` → `UIApplicationMain` →
  `CFRunLoop` → **11 кадров MapLibre** → `objc_msgSend` → **7 кадров нашего
  бинаря**, состояние `TH_RUN`. То есть MapLibre вызвал наш ObjC/Kotlin-колбэк,
  и крутится наш код.
- **thread 302356 — воркер libdispatch с `USER_INTERACTIVE`**, тоже целиком
  в нашем бинаре.
- Четыре смещения (`10423116`, `10520460`, `10551988`, `40427668`) встречаются
  в стеках **обоих** потоков — они исполняют один и тот же участок кода.
  Тот же участок бинаря (~10.4–10.6 МБ) фигурирует и в стеке потока
  `Main GC thread`, где в инциденте №1 символы были:
  `kotlin::alloc::ObjectSweepTraits::trySweepElement` / `Heap::Sweep`.
  Т.е. это регион рантайма Kotlin/Native (ObjC-interop + GC).

Символизация нашего бинаря **приблизительная** — UUID из инцидента
(`71f995ea…`) не совпадает ни с одной сохранившейся локальной сборкой
(текущая — `86A456BA…`), поэтому конкретные имена функций доверия не
заслуживают. Но район попадания устойчив и по нему видно:
внешние кадры воркера 302356 ложатся в
`androidx.compose.ui.window.SurfaceMetalRedrawer` (Metal-рендер-цикл Compose
Multiplatform на своей dispatch-очереди), а общие с главным потоком кадры —
в interop/рантайм Kotlin/Native. **Это лид, не факт.**

Итого связка, объясняющая все три инцидента одинаково:

1. Приложение входит в состояние, где два потока `USER_INTERACTIVE`
   (главный + рендер-цикл Compose) непрерывно жгут оба ядра.
2. Если в этот момент приложение уходит в фон, MapLibre синхронно и без
   таймаута блокирует главный поток на подтверждении от потока приоритета
   31, который не может получить CPU → FRONTBOARD-watchdog не дожидается
   5 секунд → `SIGKILL 0x8BADF00D` (инцидент №1).
3. Если не уходит — одна только загрузка двух ядер `USER_INTERACTIVE`-работой
   голодит системные демоны; у нас в `Info.plist` `UIBackgroundModes:
   location` и на активной записи включается
   `allowsBackgroundLocationUpdates`, т.е. процесс **не усыпляется** в фоне и
   продолжает жечь CPU. 60 секунд без ответа на ping — и watchdog
   перезагружает устройство целиком (инциденты №2 и №3).

Второй пункт — баг MapLibre. Первый и третий — наши.

### 6. Историческая справка: этот дедлок предсказали в 2017-м

Пауза файл-источников на фоне пришла из Mapbox:
[mapbox/mapbox-gl-native#8125](https://github.com/mapbox/mapbox-gl-native/pull/8125)
(«Introduce pause/resume API on default file source»). Мотив — не гонять
SQLite/сеть, когда приложение работает в фоне: при заблокированном
устройстве файл БД может быть недоступен из-за Data Protection, и это давало
«SQLite disk I/O error»-краши. В обсуждении того же PR John Firebaugh
написал про предложенный `Thread::pause`:

> I'm not sure that a `Thread::pause` approach will work. That would mean that
> if you pause the FileSource thread, and then call methods […] that use
> `invokeSync`, the application will deadlock.

Подход всё равно приняли, и он дожил до MapLibre без изменений.

### 7. Что с этим делают другие

Готового «как все делают» нет: единственный публичный след — issue #2328,
без ответа. Реалистичные варианты, по убыванию осмысленности:

1. **Убрать первопричину — прожор CPU на нашей стороне.** Без двух
   пожирающих ядра потоков `pause()` возвращается за микросекунды, и вся
   конструкция перестаёт быть опасной. Это же чинит и общесистемные
   перезагрузки (инциденты №2 и №3), на которые сам MapLibre не влияет.
2. **Снять наблюдателя MapLibre.** Он висит на синглтоне, и его можно
   отцепить из приложения:

   ```kotlin
   NSNotificationCenter.defaultCenter.removeObserver(
       observer = MLNOfflineStorage.sharedOfflineStorage,
       name = UIApplicationDidEnterBackgroundNotification,
       object = null,
   )
   ```

   Делать это надо после первого обращения к `sharedOfflineStorage`
   (иначе `dispatch_once` ещё не отработал и снимать нечего).
   Парный `unpauseFileSource:` трогать не нужно — он сам выходит по
   `if (!self.isPaused) return`.
   **Цена:** возвращается ровно то, ради чего пауза вводилась — при
   `UIBackgroundModes: location` (а он у нас есть) MapLibre может пойти в
   SQLite/сеть на заблокированном устройстве. Риск «disk I/O error» реален,
   хотя современный `OfflineDatabase` переживает такие ошибки мягче, чем
   код 2017 года.
3. **Патченый форк `maplibre-native`** (сделать `pause()` асинхронным или
   с таймаутом). Технически правильнее всего, но это своя сборка
   XCFramework и своя ветка сопровождения — против правила «кроссплатформенная
   библиотека — первый вариант» и дорого для нашего размера.
4. **Репорт в апстрим.** У нас есть то, чего нет в #2328: полный дамп всех
   потоков, доказательство, что поток-адресат простаивает, и объяснение
   через приоритеты. Это тянет на нормальный баг-репорт (с предложением
   `pause()` с таймаутом или неблокирующей паузой).

Чего делать НЕ надо: `beginBackgroundTask` не помогает — watchdog здесь
считает не «время работы в фоне», а время возврата из
`applicationDidEnterBackground`.

### 8. Что осталось неизвестным

- **Что именно жжёт CPU в двух `USER_INTERACTIVE`-потоках** — главный
  вопрос, и он теперь важнее самого MapLibre. Нужна символизация с
  бинарём той же сборки: держать `.app`/`.dSYM` каждой сборки, которую
  ставим на устройство (сейчас они перезаписываются, поэтому UUID из
  инцидента №3 уже не с чем сопоставить).
- Гипотеза «сеть пропала во время загрузки тайла» — теперь выглядит
  ненужной: поток `OnlineFileSource` в момент зависания простаивал, никакой
  сетевой операции в полёте не было.

## План действий (рекомендация 2026-09-01)

Порядок именно такой: сначала дешёвое и разблокирующее, потом снятие острого
риска, потом настоящий фикс. Шаги 1 и 3 требуют устройства — их делает
пользователь, не агент.

### Шаг 0. Перестать терять символы (сделать до всего остального)

Каждый инцидент, кроме первого, оказался нечитаемым только потому, что
`leshy.debug.dylib` той сборки уже перезаписан (UUID `71f995ea…` из инцидента
№3 не совпадает ни с одной сохранившейся копией). Пока это не починено,
любой следующий инцидент так же превратится в «два безымянных кадра».

**Сделано 2026-09-01.** Фаза `Archive symbols for crash reports` в таргете
`iosApp` → `iosApp/Scripts/archive-symbols.sh`: на каждой сборке под
`PLATFORM_NAME = iphoneos` складывает Mach-O (`leshy`, `leshy.debug.dylib`,
встроенные фреймворки включая `MapLibre`) и, в Release, `.dSYM` в
`~/Library/Developer/leshy-symbols/<время>-<конфиг>-<UUID>/`, хранит последние
10 сборок. Рядом кладётся `uuids.txt` со всеми UUID сборки и коммитом, так что
поиск по репорту — это

```bash
grep -ril <UUID-из-.ips> ~/Library/Developer/leshy-symbols/*/uuids.txt
```

Копируются только бинари, не `.app` целиком: `atos`/`dwarfdump` ресурсы не
нужны. Подробности и грабли — `iosApp/CLAUDE.md`.

### Шаг 1. Померить базовый расход CPU (30 секунд, до любого кода)

По watchdog-статистике инцидента №1 приложение сожгло `79.780с user` при
`100% CPU`. **Уточнение (иначе цифра читается неверно):** `procLaunch` =
`20:02:48`, `captureTime` = `20:07:08`, то есть процесс прожил ~260с, и 79.78с
CPU за это время — в среднем ~31% ядра, а не «полное ядро с самого запуска».
Сотня процентов относится к собственному окну наблюдения watchdog (~80с, оно
и даёт ровно 79.78с при 100%): в течение этого окна ядро было выедено
полностью. Поэтому при замере ждать надо не ровного «100% всегда», а всплеска
до полного ядра на конкретном экране — что шаг 1 и должен локализовать.

Запустить с устройства из Xcode и смотреть Debug navigator → CPU, по
очереди на каждом экране:

| Экран | Что смотреть |
|---|---|
| Запись, трек не пишется | базовый уровень |
| Запись, трек пишется | +тикер раз в секунду (`RecordViewModel.kt:676`) |
| Карта (агрегированная) | самый тяжёлый набор слоёв |
| Архив / Настройки | экраны без карты — контрольная точка |

Ключевой вопрос: **проседает ли CPU до единиц процентов на экранах без
карты?** Если да — виновата связка Compose + `UIKitView` с `MLNMapView`.
Если нет — виновато что-то общее (тикер, анимация, рекомпозиция).

Дальше — Time Profiler на 60 секунд на самом тяжёлом экране; смотреть
главный поток и очередь редроера Compose (`SurfaceMetalRedrawer`) — те
самые два потока `USER_INTERACTIVE` из стекшотов.

### Шаг 2. Снять наблюдателя `pauseFileSource:` (убирает класс инцидента №1)

Самое большое снижение риска за наименьшие деньги: убирает сам блокирующий
вызов, а значит и обе версии объяснения (голодание по CPU и потерянный
wakeup) перестают иметь значение.

Новый `single(createdAtStart = true)` в `PlatformModule.ios.kt`, рядом с
`IosPinnedStyleInterceptor`:

```kotlin
// Сначала обратиться к синглтону — наблюдателя вешает его dispatch_once,
// до первого обращения снимать нечего.
val storage = MLNOfflineStorage.sharedOfflineStorage
NSNotificationCenter.defaultCenter.removeObserver(
    observer = storage,
    name = UIApplicationDidEnterBackgroundNotification,
    `object` = null,
)
```

Парный `unpauseFileSource:` на `WillEnterForeground` трогать не надо — он
сам выходит по `if (!self.isPaused) return`.

**Цена и как её оценивать.** Пауза вводилась (mapbox-gl-native#8125), чтобы
MapLibre не лез в SQLite и сеть, пока приложение работает в фоне на
заблокированном устройстве — при Data Protection файл БД может быть
недоступен, отсюда исторические «SQLite disk I/O error». У нас
`UIBackgroundModes: location` и на активной записи включается
`allowsBackgroundLocationUpdates`, то есть процесс в фоне живой — риск не
теоретический. Смягчает то, что по умолчанию файлы контейнера идут с
`NSFileProtectionCompleteUntilFirstUserAuthentication`, то есть после
первой разблокировки с момента загрузки телефона БД доступна и на
заблокированном экране. Практически: следить, не появятся ли в логах
`disk I/O error` во время долгих прогулок с заблокированным экраном.

**Как проверять фикс:** экран с картой, активная запись трека, свернуть и
развернуть приложение 20 раз подряд — до фикса это ровно тот сценарий,
который трижды убил приложение/телефон.

### Шаг 3. Снизить расход CPU (настоящий фикс инцидентов №2 и №3)

Шаг 2 не спасает от общесистемных перезагрузок: там приложение уже никуда
не уходило (в инциденте №3 у процесса `flags: ["foreground"]`), демоны
голодали от самой загрузки. Конкретные меры расписывать до шага 1
бессмысленно, но направления, по убыванию вероятности:

1. **Compose поверх `UIKitView` с `MLNMapView`** — интероп заставляет
   композитить нативную вьюху со слоем Compose каждый кадр; на A9 это может
   стоить ~ядра. Смотреть в сторону ограничения FPS карты и остановки
   рендера, когда экран карты не на переднем плане.
2. **Тикер раз в секунду на «Записи»** (`RecordViewModel.kt:676`) — сам по
   себе дёшев, но если он дёргает рекомпозицию всего экрана вместе с картой,
   цена другая. Проверяется изоляцией состояния таймера.
3. **Легитимная стоимость 60fps векторной карты на iPhone SE 1** — вариант,
   который надо честно рассмотреть: если после шага 1 окажется, что это не
   баг, а цена устройства 2015 года, то шаг 2 становится не временной мерой,
   а постоянной, и к нему добавляется ограничение частоты кадров.

### Шаг 4. MetricKit — чтобы следующий инцидент разобрался сам

**Сделано 2026-09-01.** `DiagnosticsArchive`
(`iosApp/iosApp/DiagnosticsArchive.swift`), подписка из
`AppDelegate.application(_:didFinishLaunchingWithOptions:)`. Складывает
`jsonRepresentation()` каждого `MXDiagnosticPayload` в
`Application Support/diagnostics/` (имя файла несёт счётчики:
`…-diagnostic-hang1-cpu0-crash0-disk0.json`), длительности зависаний и
`totalCPUTime` дублирует в syslog. На старте дочитывает
`pastDiagnosticPayloads`/`pastPayloads` — системный буфер за 7 суток.

Две вещи сверх исходного плана:

- **`MXMetricPayload` сохраняется тоже.** В нём `cpuMetrics.cumulativeCPUTime`
  за сутки реального пользования — фактически шаг 1, снятый в поле, а не в
  Instruments, и без участия пользователя.
- **Файлы в `Application Support`, не в `Documents`.** Забирать их
  `idevicecrashreport`, как предполагал исходный план, нельзя — он тянет
  только `.ips` из CrashReporter; вариант «из Files» потребовал бы
  `UIFileSharingEnabled`, то есть открыл бы наружу и данные пользователя.
  Забирается выгрузкой контейнера из Xcode → Devices and Simulators.

Расписание доставки не наше: система отдаёт payload'ы не чаще раза в сутки
и обычно на следующем запуске после события — сразу после зависания файла не
будет. Проверять сам код — Xcode → Debug → Simulate MetricKit Payloads.

### Шаг 5. Отчёт в апстрим

Дописать в maplibre/maplibre-native#2328: у нас есть то, чего нет в
исходном сообщении — полный дамп всех потоков, доказательство, что
поток-адресат в момент зависания простаивал в пустом `CFRunLoopRun`,
разбор через приоритеты (47 против 31) и то, что подписку получает любое
приложение с картой через `MLNMapView.mm:718`. Предложение по фиксу:
`pause()` с таймаутом либо неблокирующая пауза (поставить задачу в очередь
и не ждать подтверждения).

### Чего делать не надо

- **`beginBackgroundTask`** — watchdog здесь считает не время работы в фоне,
  а время возврата из `applicationDidEnterBackground`.
- **Форк `maplibre-native` как первый шаг** — своя сборка XCFramework и своя
  ветка сопровождения; браться только если шаги 2 и 3 не сработают.
- **Искать пропажу сети** — гипотеза снята, поток `OnlineFileSource` в
  момент зависания не имел ни одной операции в полёте.
