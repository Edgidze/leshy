# План: подборки по странам + мультиязычность

Замена демо-подборок (север/юг/восток) на 33 подборки по странам из
408-категорийного каталога, и расширение приложения с 2 до 26 языков
интерфейса при 35 языках названий грибов.

Статус решений: набор языков интерфейса — **26 государственных**;
экран выбора языка показывает **все языки сразу**, непереведённый интерфейс
падает на английский (см. «Решения», п. 4).

---

## 1. Что пришло во входных данных

`leshy_core_app.json` (856 КБ, `schema_version: 3`) — проверено скриптом:

| | |
|---|---|
| Категорий | 408 (`GC0001`…), у всех есть `sci` и `image` |
| Языков названий | 36 (`labels`), из них 35 фигурируют в пресетах стран |
| Стран | 33, все позиции со статусом `CORE`; размер набора **не фиксирован** — 50 у большинства, 55 у `RS`, 54 у `RU` после добавлений (см. 3.3) |
| Уникальных категорий по всем странам | 408 — каталог ровно равен объединению CORE-подборок. **Отдельного отбора «что CORE» делать не нужно: берётся всё из файлов** |
| Позиций без названия на языке страны (`needs_name`) | 14 из 1655 (BY — 5, MX — 8, ES — 1) |
| `breadth` | narrow 318 / mid 55 / broad 35 |
| Категорий с совпадающим `sci` | 13 пар (ключи `..._2`), это разные народные концепты при одном латинском имени |

`app_assets_256/mushrooms/` — 408 webp 256×256 с альфой, **1:1 с
категориями**: ни одного файла без категории, ни одной категории без файла,
имена файлов берутся из поля `image` и **не выводятся из `key`**: у
13 категорий-дублей ключ содержит два подчёркивания
(`gyromitra_esculenta__2`), а файл — одно (`gyromitra_esculenta_2.webp`).

`images_index.json` (464 КБ) — из полезного только `category_id → file`, что
уже есть в `leshy_core_app.json`. `reference_credits` — 173 КБ, не нужны
(референсные изображения в приложении не показываются). **Файл целиком не
переносится в проект.**

Покрытие названиями глобально разреженное (ru 34%, en 46%, de 21%, ja 14%,
mi 2%), но внутри своей страны почти полное — отсюда правило фолбэка на
научное имя работает в основном при «чужих» комбинациях (японский интерфейс +
российская подборка), а не внутри одной страны.

### Чего в данных нет

- **Цветов маркеров.** Нынешние 30 категорий имеют выверенный вручную
  `colorHex`, у 408 новых — ничего. Генерируются в Фазе 0, алгоритм — 3.5.
- **Названий стран** ни на одном языке, кроме английского (`country`).

## 2. Перевод интерфейса: Клод или DeepL

**Ответ: Клод. DeepL здесь не окупается ни деньгами, ни качеством.**

Объём измерен, он крошечный: 271 `StringKey`, английская ветка — **3 883
знака**, русская — 4 207. То есть один язык ≈ 4 КБ текста (~900 слов), 24
новых языка ≈ **101 тыс. знаков**.

| | Клод | DeepL API |
|---|---|---|
| Деньги | в рамках подписки | Free-тариф 500 тыс. знаков/мес → **0 ₽**; Pro ≈ €2 разово |
| Покрытие 26 языков | все | **22 из 26**: нет `be`, `hr`, `ka`, `sr` — 4 языка всё равно на Клоде |
| Формы множественного числа | делает по CLDR-категориям | **не умеет принципиально** — переводит одну форму, а нужны `гриб/гриба/грибов` для pl, cs, lt, sl (двойственное!), ro |
| Контекст UI | видит `StringKey`, соседние строки, весь экран | «Запись», «Сбор», «Данные» без контекста переводятся наугад; глоссарий — только Pro и не для всех пар |
| Ограничение длины | можно задать («табы ≤ 12 знаков») и проверить | нет |
| Выход | сразу `.kt` с готовой `mapOf` | JSON → нужен скрипт, ключ API, кодогенерация |
| Терминология домена | «тихая охота», «находка», «отметка», «прогулка» держатся согласованно | рассыпается между строками |

Решающее — не цена (она нулевая в обоих случаях), а то, что **плюральные
формы и однословные UI-подписи** — это ровно те два класса строк, где
машинный перевод без контекста ломается, и их в этих 271 ключах
непропорционально много.

DeepL остаётся полезен как **выборочная сверка**: после того как язык
переведён, прогнать 20–30 спорных строк обратно (target→ru) и посмотреть на
расхождения. Это ручная операция на 5 минут, API не нужен.

Стоимость на Клоде: ~4–5 КБ вывода на язык ≈ 2,5 тыс. output-токенов плюс
проверка. **4 языка за сессию** — комфортный шаг, 6 сессий на все 24.

## 3. Архитектура

### 3.1 Названия грибов уходят из `StringKey`

408 категорий × 36 языков = до 14,7 тыс. строк. Через `StringKey` + exhaustive
`when` это нереализуемо, и правило «локализация только через ключи»
(корневой `CLAUDE.md`, п. 2) здесь перестаёт масштабироваться — как оно уже
перестало для своих видов грибов (`customNames`, см. `i18n/CLAUDE.md`).
Названия каталога становятся **данными**, а не ключами:

```
composeResources/files/catalog/
  catalog.json            408 × {key, sci, image, color, breadth, importance, dangerous}   ~60 КБ
  countries.json          33 × {code, langs, keys[]}                                        ~40 КБ
  names/<lang>.json       36 файлов, {key: name}                                        1–15 КБ
  countries/<lang>.json   26 файлов, {countryCode: name}                                 ~1 КБ
```

`files/` — распознаваемая Compose Resources typed-папка, читается
`Res.readBytes("files/...")` (уже используется в `SpeciesFormDialog.kt:182`
для drawable). Ограничение из `.claude/rules/compose-resources.md` про
файлы верхнего уровня не нарушается.

Разбивка названий по языкам, а не один общий файл — чтобы в память грузился
только активный язык (15 КБ вместо 500 КБ) и переключение языка не стоило
разбора всего каталога.

**Правило отображения имени** (`categoryDisplayName`):
свой вид → `customNames` → иначе `names[<активный язык>][key]` → иначе
`sci`. Никакого промежуточного фолбэка на английский: пользователь просил
именно научное имя, и это честнее — «Amanita muscaria» однозначна, а
английское имя в японском интерфейсе выглядит как баг.

### 3.2 Переводы интерфейса — генерируемые Kotlin-таблицы

`StringKey` (enum) и exhaustive `when` для **ru/en остаются как есть** — это
базовые языки, и компилятор продолжает ловить забытый ключ при добавлении
новой строки, ровно как задумано в `i18n/CLAUDE.md`. Остальные 24 языка —
по файлу `i18n/strings/StringsDe.kt` вида:

```kotlin
internal val germanStrings: Map<StringKey, String> = mapOf(
    StringKey.AppName to "Leshy: Pilzkarte",
    ...
)
```

и резолвер:

```kotlin
fun string(key: StringKey, language: AppLanguage): String = when (language) {
    AppLanguage.RU -> russianStrings(key)
    AppLanguage.EN -> englishStrings(key)
    else -> uiTranslations[language]?.get(key) ?: englishStrings(key)
}
```

Почему Kotlin-таблицы, а не JSON в ресурсах: синхронно, без async-загрузки при
старте и переключении, без состояния загрузки в `App()`, опечатка в имени
ключа — ошибка компиляции. Цена — ~7 тыс. строк сгенерированного Kotlin, для
бинарника это шум.

Компилятор больше не гарантирует полноту неанглийских карт — вместо него
**тест в `commonTest`**: каждая карта покрывает все `StringKey`, значения
непустые, нет дублей. Пропущенный ключ деградирует до английского, а не
ломает сборку — для 24 языков это правильный компромисс.

### 3.3 Категории и подборки в Room

Категории остаются в Room (нужен FK от `objects`, плюс пользовательские
`isActive`/`isPicked`), но каталог из 408 строк — источник истины в
`catalog.json`, а не в `DEFAULT_CATEGORIES` в коде.

`nameKey` каталожной строки становится ключом каталога (`amanita_muscaria`), а
не `category_amanita_muscaria`. **Миграция обязана переименовать, а не
пересоздать** — `objects.categoryId` каскадится от `categories` (v7→v8), любой
`DELETE` унесёт находки пользователя.

Совпадение старых 30 ключей с новым каталогом проверено: 23 совпадают
буква-в-букву после снятия префикса `category_`, 7 получают явное
соответствие (**задано владельцем проекта, ключ соответствия — GC-код**):

| Старый `nameKey` | GC | Новый `nameKey` |
|---|---|---|
| `category_russula_species` | `GC0034` | `russula_cyanoxantha` |
| `category_agaricus_species` | `GC0032` | `agaricus_campestris` |
| `category_morchella_species` | `GC0012` | `morchella_esculenta` |
| `category_gyromitra_species` | `GC0108` | `gyromitra_esculenta__2` |
| `category_lycoperdon_calvatia_species` | `GC0074` | `lycoperdon_perlatum` |
| `category_xerocomus_subtomentosus_group` | `GC0065` | `xerocomus_subtomentosus` |
| `category_suillus_luteus` | `GC0056` | `suillus_luteus__2` (не прямое совпадение — см. ниже) |

Все семь целей уже входят в `RU`-пресет — переименование не выкидывает
пользовательские находки из российской подборки. (Ради этого `GC0056` и
выбран вместо буквального `suillus_luteus`.)

### Правки `RU`-пресета

Проверка вскрыла, что **из 30 нынешних категорий приложения в присланный
`RU`-пресет не попали шесть**. Для уже установленных копий это было бы
безобидно (миграция не трогает `isPicked`), но новый российский пользователь
этих грибов в подборке не увидел бы вовсе. Решения владельца проекта:

| GC | Ключ | Решение |
|---|---|---|
| `GC0094` | `amanita_vaginata` | добавить в `RU` |
| `GC0007` | `coprinus_comatus` | добавить в `RU` |
| `GC0048` | `craterellus_tubaeformis` | добавить в `RU` |
| `GC0031` | `hygrophoropsis_aurantiaca` | добавить в `RU` |
| `GC0056` | `suillus_luteus__2` | уже в `RU`; **старый `category_suillus_luteus` переименовывается в него**, а не в `suillus_luteus` (`GC0023`) — старая единственная запись «маслёнок» ложится на широкий концепт, который и так в наборе |
| `GC0011` | `armillaria_mellea` | добавить в `RU`, см. ниже |

**Опёнок.** В каталоге две записи, и `RU` содержал не ту:

| GC | Ключ | `sci` | В скольких пресетах | Решение |
|---|---|---|---|---|
| `GC0011` | `armillaria_mellea` | *Armillaria mellea* | 24 | **добавить в `RU`**, переименовать в «Опёнок осенний» |
| `GC0165` | `armillaria_borealis` | *Armillaria borealis* | 2 (`FI`, `RU`) | **убрать из `RU`**, переименовать в «Опята осенние» |

`GC0011` — магистральный концепт опёнка по всему каталогу
(`importance 5.0`, «Honey fungus»), и именно в него переименовывается
нынешний `category_armillaria_mellea`; без правки прошлые находки опёнка
уехали бы в категорию, которой в российской подборке нет. `GC0165` после
правки остаётся только в `FI`, так что его русское имя видно лишь при
финской подборке с русским интерфейсом — то есть обмен именами ничего не
ломает.

Русские имена меняются местами ради **единственного числа**: в `RU` все
прочие опята записаны в единственном («Опёнок летний», «Опёнок зимний»,
«Опёнок луговой», «Ложноопёнок серно-жёлтый», «Ложноопёнок
кирпично-красный») — проверено по всем 54 позициям, «Опята осенние» было
единственным множественным именем во всём наборе. «Опёнок осенний» уже
присутствует в `alt_names.ru` у `GC0011`, так что это повышение
существующего синонима до основного, а не выдумывание нового.

Итог: `RU` — **54 позиции** (50 − `GC0165` + `GC0094`, `GC0007`, `GC0048`,
`GC0031`, `GC0011`).

Подборки: `collections` получает 33 строки `collection_country_<cc>`, три
`collection_demo_*` удаляются (вместе с их cross-ref — каскад по
`category_collections`, категории при этом не трогаются). `isPicked`
пользователя не сбрасывается ни при каких условиях.

### 3.4 Откуда берётся имя гриба: два источника, а не один

В `leshy_core_app.json` названия лежат **в двух местах**, и они расходятся:
`categories[].labels[lang]` (глобальное имя категории) и
`country_presets[].items[].names[lang]` (имя в контексте конкретной страны).
Измерено: из 2193 пар «страна × позиция × язык» **174 (7,9%) расходятся**, и
104 пары «категория + язык» названы по-разному в разных странах.

Но это почти не региональные различия, а разнобой в записи одного и того же
имени, причём систематически в одну сторону — `labels` тяготеет к
множественному числу и широким формам, `names` в пресетах к единственному и
конкретным:

| `labels` | `names` в пресете |
|---|---|
| Deathcap | Death cap |
| Saffron milkcap | Saffron milk cap |
| Champignons | Champignon |
| Karbolegerlinge | Karbolchampignon |
| Rauköpfe | Orangefuchsiger Raukopf |
| Fichten-Reizker | Fichtenreizker |

То есть **пресетные имена — лучший источник**, и ровно в том направлении,
которое нужно (единственное число, см. историю с опёнком выше).

Архитектуре при этом нужно **одно** имя на пару «категория + язык»: категория
может входить в несколько выбранных подборок одновременно, и зависимость
имени от того, «через какую страну» гриб попал в список, была бы источником
странностей. Поэтому Фаза 0 сливает источники по фиксированному правилу:

1. если для пары есть пресетные имена — взять имя из страны, где этот язык
   основной; при нескольких таких странах или их отсутствии — самое частое;
2. иначе — `labels[lang]`;
3. поверх всего — файл ручных переопределений (см. ниже).

Правило проверено на итоговом `RU`: из 54 позиций оно меняет **одну** —
`GC0094` с «Толкачик» (`labels`) на «Поплавок серый» (пресет `MD`), то есть
на то самое имя, под которым эта категория и запрашивалась. Остальные 53
совпадают.

**Ручные переопределения — `docs/catalog/name_overrides.json`**, применяются
генератором Фазы 0 последним слоем. Нужны потому, что правило слияния
детерминированное и правки «по факту» в сгенерированных файлах умрут при
первой же перегенерации. Первые две записи — обмен именами опят:

```json
{ "GC0011": { "ru": "Опёнок осенний" },
  "GC0165": { "ru": "Опята осенние" } }
```

### 3.5 Цвета маркеров — доминирующий цвет иллюстрации

Берётся тот же приём, что уже работает для пользовательского вида:
`dominantHue` в `SpeciesFormDialog.kt` — один проход по пикселям, бины по
10° оттенка с весом по насыщенности, отбрасываются почти-серые
(`s < 0.15`), почти-чёрные (`v < 0.12`) и почти-белые (`v > 0.97`) пиксели
как фон/тень/блик. Для webp с альфой добавляется отбрасывание прозрачных
(`a < 0.5`) — у пользовательских PNG альфы не было, поэтому в оригинале
этого условия нет.

**Но одного оттенка мало, и это измерено.** Прогон алгоритма как есть по всем
408 иллюстрациям:

- 185 категорий из 408 попали в один бин (35°), ещё 108 — в соседний (25°);
- **в среднем 7,8 различимых цветов на страну** при 50 видах в подборке,
  в худшем случае (LT) — 6 цветов, крупнейшая группа 25 видов одного цвета.

Причина не в алгоритме, а в том, что грибы коричневые, и в том, что
`SpeciesFormDialog` фиксирует `S = 0.75`, `V = 0.62` константами — для
одного пользовательского вида это не важно (он один, и есть ползунок), для
50 маркеров на карте это схлопывает всё в одну краску. Показательно, что
**нынешние 30 ручных цветов лежат в тех же 7 бинах оттенка** (8°…59° плюс два
красных) — различает их именно светлота: от `#E6E0D4` до `#7F2F14`.

Поэтому S и V тоже берутся из изображения — средние по пикселям
победившего бина, с зажимом в читаемый на карте диапазон
`S ∈ [0.35, 0.85]`, `V ∈ [0.45, 0.80]`. Измерено на тех же 408 файлах:

- **в среднем 48,4 различимых цвета на страну** из ~50, крупнейшая группа — 3;
- 372 различимых цвета на 408 категорий;
- у `RU` — 50 разных цветов на 50 видов, ни одного повтора.

Бледный дождевик получает бледный маркер, тёмный польский гриб — тёмный,
то есть связь «цвет ↔ иллюстрация» сохраняется, ради которой приём и брался.

Нынешние 30 ручных цветов **пересчитываются вместе со всеми** — единый
алгоритм на весь каталог важнее, чем сохранение ручной подгонки для 7%
категорий, тем более что диапазон у них тот же.

### 3.6 Производительность сида

`EnsureDefaultCategoriesUseCase` сейчас делает `getByNameKey` в цикле — на 408
категориях это 408 запросов на **каждом** запуске, плюс 1655 `addMember` для
подборок. Переделать на: одна выборка `getAll()` → диф в памяти → batch-upsert,
и гейт по `catalogVersion` в DataStore — полный проход только когда версия
встроенного каталога изменилась.

## 4. Решения, зафиксированные до начала работ

1. **26 языков интерфейса**: be, bg, cs, de, en, es, et, fi, fr, hr, hu, it,
   ja, ka, ko, lt, lv, pl, ro, ru, sk, sl, sr, sv, tr, uk. Региональные
   (ca, eu, gl) и индигенные (nah, tsz, tzo, maa, hch, mi) — только языки
   названий грибов: они есть в `names/<lang>.json`, но не в `AppLanguage`.
   При выборе, скажем, каталонского интерфейса нет — а каталонские названия
   грибов будут доступны только когда/если ca войдёт в `AppLanguage`.
2. **`sr-Cyrl` не отдельный язык интерфейса.** В `labels` он есть; в
   `AppLanguage` — только `sr`. Кириллический сербский попадёт в
   `names/sr-Cyrl.json` и останется зарезервированным на будущее.
3. **Все 408 категорий сидируются в Room всегда**, независимо от выбранных
   стран. 408 строк — ничто для SQLite, а `isPicked`/`isFilterEligible` уже
   решают, что предлагать пользователю. Так подборку можно переключить
   офлайн и мгновенно.
4. **Экран выбора языка показывает все 26 сразу**, интерфейс непереведённых
   падает на английский. Это делает Фазы 6–11 полностью независимыми: каждая
   пачка переводов — один коммит в `i18n/strings/`, без правок UI и без
   правок списка языков.
5. **Названия языков в списке — эндонимы** (Deutsch, Français, 日本語,
   ქართული), плюс английское имя мелким шрифтом второй строкой. Переводить
   26 × 26 названий языков не нужно вообще, и эндоним — то, что человек
   узнаёт, даже когда приложение сейчас на незнакомом ему языке.
6. **Названия стран переводятся** (33 × 26 ≈ +10 тыс. знаков суммарно, ~400
   знаков на язык — в шумах на фоне 4 КБ интерфейса), идут теми же пачками,
   что и интерфейс, в `countries/<lang>.json`.
7. **`leshy_core_app.json` остаётся в репозитории** как `docs/catalog/leshy_core_app.json`
   — 856 КБ за возможность перегенерировать все производные файлы.
   `app_assets_256/` расформировывается: 408 webp → `composeResources/drawable/`,
   `images_index.json` удаляется целиком.
8. **Форма своего вида не меняется.** Проверено: `SpeciesFormDialog` уже
   принимает один `language` и правит `customNames[language]` — 26 полей
   ввода не появится. `Converters.toCustomNames` и `SettingsRepositoryImpl
   .observeLanguage` уже ищут язык через `find`/`firstOrNull` по `code`, то
   есть **расширение enum аддитивно и не требует миграции**; неизвестный код
   (откат версии приложения) деградирует, а не падает.

## 5. Фазы

Каждая фаза — отдельная сессия, заканчивается компилируемым и проверяемым на
устройстве состоянием. Ничего не ломается посередине: до Фазы 4 приложение
внешне остаётся двуязычным.

### Фаза 0 — генератор ассетов (без кода приложения)

`tools/build_catalog.py`:
- читает `docs/catalog/leshy_core_app.json`, пишет `catalog.json`,
  `countries.json`, 36 × `names/<lang>.json`;
- имена собирает по правилу слияния 3.4 (пресетные `names` → `labels` →
  `docs/catalog/name_overrides.json`), правки `RU`-пресета из 3.3 применяет
  здесь же — **никаких ручных правок в сгенерированных файлах**, иначе они
  умрут при следующей перегенерации;
- копирует 408 webp из `app_assets_256/mushrooms/` в

  `xerocomus_subtomentosus_group`). **`unknown_mushroom.webp` и

- считает `colorHex` по алгоритму 3.5 (Pillow 11.3 в системе уже есть),

Затем: `app_assets_256/` удаляется, `leshy_core_app.json` переезжает в `docs/catalog/`.

Проверка: `./gradlew :shared:compileAndroidMain` — Compose Resources
генерирует 410 аксессоров вместо 32 (408 каталожных + `unknown_mushroom` +
`leshy_logo`). **Риск:** заметный рост времени задачи

## 7. Какие фазы делать на Opus, какие на Sonnet

Правило одно: **Opus там, где ошибку не поймает ни компилятор, ни тест, ни
собственный взгляд владельца проекта.** Везде, где есть быстрая объективная
обратная связь, Sonnet дешевле и достаточен.

| Фаза | Модель | Почему |
|---|---|---|
| 0 — генератор ассетов | Sonnet | Результат проверяется запуском скрипта, ожидаемые числа известны заранее и записаны в плане. Ошибка видна сразу |
| 1 — слой каталога | Sonnet | Exhaustive `when` и компилятор ловят почти всё; структура данных уже зафиксирована в разделе 3 |
| **2 — миграция Room** | **Opus** | Единственная фаза с риском для данных пользователя. Необратимо, каскад `ON DELETE` от `categories` к `objects`, SQLite не умеет `ALTER` внешние ключи. Ошибка проявится у людей с записанными прогулками после обновления, откатить будет нечем |
| 3 — подборки по странам | Sonnet | Ошибки видны глазами на экране |
| 4 — язык и экран выбора | Sonnet | Механическая работа по готовому описанию; совместимость уже проверена (расширение enum аддитивно) |
| **5 — плюральные формы** | **Opus** | Правила CLDR на 26 языков: словенское двойственное число, литовские исключения, румынское «few» для `0` и `1–19 mod 100`. Ошибка тихая — приложение работает, просто в одном языке из двадцати шести неправильная форма слова, и никто этого не заметит |
| 6, 7, 8 — переводы (de/fr/es/it, pl/cs/uk/sv, ja/ko/tr/ro) | Sonnet | Языки с большим объёмом данных, разница в качестве микрокопии мала |
| **9, 10, 11 — переводы (be/bg/sr/hr, sk/sl/hu/fi, lt/lv/et/ka)** | **Opus** | Низкоресурсные языки, где машинный и «дешёвый» перевод скатывается в кальку с английского и неестественный регистр. Проверить это самостоятельно нельзя, обратной связи не будет до жалоб пользователей — тот же принцип, что и с миграцией |
| 12 — уборка и проверка | Sonnet | Измерения и правка документации |

Итого **5 сессий на Opus** (2, 5, 9, 10, 11) из 13.

Важное для расчёта бюджета: дорого не «Opus», а «Opus × большой контекст».
Переводческие сессии контекстно почти пустые — 271 строка, глоссарий и
никакого чтения кодовой базы, вывод 4–5 КБ на язык. Три переводческие
сессии на Opus обойдутся дешевле, чем одна Фаза 3 на Opus с чтением
экранов и репозиториев. Поэтому распределение выше не «Opus на самое
сложное», а «Opus на самое непроверяемое, начиная с того, что дёшево».

Если бюджет всё-таки поджимает, сокращать в таком порядке: сначала Фаза 11 →
Sonnet (балтийские языки всё же ближе к европейскому мейнстриму, чем
грузинский — его одного можно оставить на Opus отдельным коротким заходом),
потом Фаза 10, потом Фаза 9. **Фазы 2 и 5 не сокращать** — это те две, где
Sonnet может тихо ошибиться так, что выяснится через месяцы.

(`mushroomsUnitLabel`/`walksUnitLabel`/`regionsUnitLabel`) — теперь по одной
строке каждый поверх общего `pluralLabel(forms, count)`; шесть ключей юнита
собраны в `PluralForms` (`Strings.kt`). Русская ветка `when` заполнена по
достижимым формам (`One`/`Few`/`Many`), недостижимые повторяют родительный
падеж множественного; английская заполнена целиком, потому что **английские
формы — это то, во что деградирует непереведённый язык, форма за формой**
(`string()` → `englishStrings(key)`), а не только две достижимые.

**Отклонение от плана — шестая категория `Zero`.** План (§5) перечисляет
пять (`One`, `Two`, `Few`, `Many`, `Other`), но латышскому `zero` нужен
по-настоящему: `lv` кладёт 0, каждое кратное десяти и весь диапазон 11–19 в
форму, отличную от `other` («10 sēņu» против «2 sēnes»). Свернуть её в
`other` значило бы выдавать неправильное слово на большой доле реальных
значений — а это ровно то, что «никто не заметит». Из 26 языков `zero` есть
только у `lv`; `two`, как план и говорил, — только у `sl`.

**Уточнение к формулировке плана про румынский.** План говорит «румынское
few для `0` и `1–19 mod 100`»; в CLDR окно `few` — `n % 100 = 2..19` плюс
`n = 0`, а `1` — это `one`. Существенно на `101` (`n % 100 = 1`, но `i ≠ 1`)
— это `other`, не `one` и не `few`; в тесте зафиксировано явно.

**Тест — `commonTest/i18n/PluralsTest.kt`, 4 теста, реально прогнан**
(`testAndroidHostTest`, зелёный; от `Res.readBytes`/Android `Context` не
зависит, в отличие от `CatalogSourceTest`/`MushroomNamesTest`). Таблица
«язык → счёт → ожидаемая категория» выписана из sample-значений CLDR, а не
выведена из реализации, и включает все граничные значения плюс места, где
однокоренные языки расходятся: польское 21 (`many`) против русского 21
(`one`), чешское 22 (`other`) против польского 22 (`few`), хорватское 5
(`other`) против русского 5 (`many`), литовские 11–19 (`other`) против
русских 11–14 (`many`), словенское 102 (`two`). Отдельные тесты: ни один
`AppLanguage` не забыт в самой таблице; у каждого юнита шесть различных
непустых ключей в обеих базовых ветках; отрицательные счётчики зеркалят
положительные (CLDR-операнд `n` — модуль; внутри взят `abs` от `Long`, чтобы
`Int.MIN_VALUE` не переполнился).

## Решения, принятые после Фазы 5 (2026-08-25)

### Плюральные ключи грибов остаются, хотя не показываются

`mushroomsUnitLabel` не вызывается ни из одного файла UI (проверено грепом по
всему `ui/`) — шесть ключей `WalkDetailMushroomsCount*` сейчас невидимы.
Решение владельца проекта: **оставить**. Ключи названы `WalkDetail…`, то есть
это невключённая задумка (счётчик находок на детали прогулки), а не мусор;
шесть ключей из 280 — 2% пачки перевода, вернуть их после 24 переведённых
языков стоило бы несравнимо дороже. Фазам 6–11 переводить их как обычно,
Фазе 12 не пересматривать это заново — вопрос закрыт.

### Названия стран — из CLDR, а не рукописными таблицами (правка §4.6)

Фаза 3 сгенерировала `countries/ru.json` из рукописной таблицы
`RU_COUNTRY_NAMES` в `tools/build_catalog.py`, и §4.6 плана предполагал, что
остальные 24 языка пойдут так же — рукописными таблицами внутри переводческих
пачек. **Отменяется: названия стран берутся из CLDR и генерируются разом на
все 26 языков**, то есть выпадают из Фаз 6–11 целиком.

Проверено на месте (`babel` 2.18, он же поставляет данные CLDR):

- все **33 кода стран** присутствуют во всех проверенных языках, включая
  низкоресурсные — `ka`, `be`, `sr`, `hr`, `lv`; ни одного пропуска;
- **английский совпадает с CLDR буква-в-букву** (0 расхождений из 33) —
  поле `country` источника и есть форма CLDR;
- **русский расходится ровно в двух местах**, и в обоих рукописный вариант
  лучше для списка: `US` — «США» против CLDR «Соединенные Штаты», `KR` —
  «Южная Корея» против CLDR «Республика Корея».

Причина расхождения: у CLDR есть короткие формы (`alt="short"`), но `babel`
отдаёт через `Locale.territories` только основную. То же будет и в других
языках (`de` даст «Vereinigte Staaten», а списку нужно «USA»).

Поэтому генератор строится **тем же двухслойным приёмом, что уже принят для
имён грибов** (§3.4): CLDR как основа + файл ручных переопределений
`docs/catalog/country_name_overrides.json` последним слоем. Никаких правок
прямо в сгенерированных `countries/<lang>.json` — они умрут при первой
перегенерации.

Зависимость: `babel` — новый импорт `tools/build_catalog.py`, **в приложение
не попадает** и стоит в том же ряду, что уже требуемый там Pillow (в системном
python его сейчас нет, ставится в venv). Если такой зависимости не хочется —
альтернатива — снять срез 33 × 26 = 858 названий один раз и закоммитить его в
`docs/catalog/`, как уже закоммичен `leshy_core_app.json` (§4.7); скрипт тогда
читает срез, а не библиотеку.

Работа небольшая и делает Фазу 6 чисто переводческой, поэтому её место —
перед Фазой 6, а не внутри неё.

**Названия стран сгенерированы (2026-08-25).** Решение выше исполнено:
`tools/build_catalog.py` больше не содержит `RU_COUNTRY_NAMES`, вместо неё —
`write_country_names()` поверх CLDR (`babel`), пишущая `countries/<lang>.json`
на **все 26 языков** сразу, плюс флаг `--only-country-names` (остальные секции
скрипта требуют удалённый `app_assets_256/`, эта — нет; разовый снипет из
Фазы 3 больше не нужен). Список языков разбирается регуляркой прямо из
`AppLanguage.kt` — 27-й язык подхватится сам. Ручной слой —
`docs/catalog/country_name_overrides.json`, две русские записи (`US`, `KR`).

Сверка: 26 файлов × 33 кода, ни одного пропуска и ни одного пустого значения;
**`en.json` и `ru.json` не изменились ни на байт** против рукописных версий
Фазы 3 — CLDR плюс два переопределения воспроизвели ровно то, что уже
проверено на устройстве; повторный прогон не меняет ни одного файла.
Зелёные: `:shared:compileAndroidMain`, `:shared:compileKotlinIosSimulatorArm64`,
`:androidApp:assembleDebug`, `:shared:testAndroidHostTest` (та же база 32/5).

Незакрытое, намеренно: CLDR даёт формальную форму, и в ряде языков она
длиннее уместной — немецкое «Vereinigte Staaten» против «USA». Переводческая
сессия, берущая язык, видит его 33 названия целиком и может добавить короткие
формы в файл переопределений; угадывать это за 24 языка сразу не стали.

**Фаза 6 теперь чисто переводческая** — только `i18n/strings/Strings<Xx>.kt`,
никаких таблиц стран.
