# Задача 7 — обрезка полей у изображений грибов: анализ и вопрос владельцу

## Вопрос, который был задан

> Будет ли негативно сказываться на качестве иллюстрирующих изображений
> грибов, если для каждого изображения произвести обрезку полей по бокам и
> сверху, снизу, чтобы собственно гриб занимал максимальное пространство на
> площади предоставленной картинке?

## Что показали измерения

Замерено по всем 410 файлам `shared/src/commonMain/composeResources/drawable/*.webp`
(скрипт разовый, в репозиторий не клался).

**Полей по бокам почти нет, поля есть сверху/снизу.** Холст 256×256 (у 408
из 410 файлов), непрозрачная часть занимает:

| ось | медиана | минимум |
|---|---|---|
| ширина | **94.5 %** (поля по 7 px с каждой стороны) | 63 % |
| высота | **75 %** | 35 % |

То есть грибы уже прижаты к левому и правому краю, а вертикальные поля
существуют потому, что почти все изображения шире, чем выше.

**Формат — lossy.** 408 файлов из 410 — VP8 (lossy) с отдельным lossless
alpha-каналом (`VP8X`+`ALPH`+`VP8 `). Значит любая обрезка требует ВТОРОГО
lossy-кодирования: сама по себе обрезка ничего не теряет, а вот пересохранение —
теряет.

**Сколько именно теряет второе кодирование** (30 случайных файлов, PSNR
пересохранённого против оригинала, и суммарный размер после обрезки):

| качество | размер от оригинала | PSNR медиана | PSNR минимум |
|---|---|---|---|
| q=70 | 84 % | 35.5 dB | 32.5 dB |
| q=75 | 86 % | 36.2 dB | 32.9 dB |
| q=80 | 94 % | 39.4 dB | 33.9 dB |
| q=85 | 104 % | 40.4 dB | 35.8 dB |
| q=90 | 118 % | — | — |
| q=95 | 138 % | 41.9 dB | 36.3 dB |
| lossless | 287 % (7.8 МБ → ~22 МБ) | без новых потерь | — |

Ориентир: выше ~40 dB отличие обычно не видно глазом, 33–36 dB заметно при
внимательном сравнении. Обратите внимание: даже q=90 даёт файлы БОЛЬШЕ
оригиналов при меньшем разрешении — значит исходники кодировались более
эффективным энкодером (`cwebp`), чем доступный здесь (PIL).

## Что обрезка реально даст на экране

**Заметный выигрыш ровно в одном месте — плитка на экране «Запись».** Слот
там 120×80 dp (`MushroomTile`: `fillMaxWidth().aspectRatio(1.5f)`), картинка
вписывается `ContentScale.Fit`:

- сейчас: квадрат 256×256 вписывается как 80×80 dp, то есть занимает лишь
  67 % ширины плитки; сам гриб — примерно 76×60 dp;
- после обрезки (медианный bbox 242×192, соотношение 1.26): вписывается как
  101×80 dp, гриб занимает всю эту площадь;
- **прирост по линейному размеру +33 %, по площади +78 %.**

**Везде остальное — квадратные слоты, выигрыш ~6 %.** Маркер на карте
(64 dp), строка экрана фильтра (56 dp), сетка «Мои грибы» — все квадратные,
а по ширине картинки уже заполнены на 94.5 %.

**Цена по разрешению.** При плотности 3× плитка «Записи» после обрезки
потребует 303 px на 101 dp, а в источнике останется 242 px — апскейл 1.25×
там, где сейчас апскейла нет вовсе (76 dp × 3 = 227 px ≤ 242 px). Маркеры на
карте при максимальном значении настройки размера апскейлятся уже сейчас
(1.5×), после обрезки станет 1.6× — разница несущественная.

## Итог

Прямой ответ на вопрос: **обрезка сама по себе качество не портит; портит
его обязательное пересохранение lossy-формата, и цена зависит от выбранного
качества.** При этом весь заметный выигрыш достаётся одному экрану, а не
всем.

## Что я предлагаю выбрать (нужно ваше решение)

1. **Ничего не делать.** Выигрыш в квадратных слотах ~6 % не стоит второго
   lossy-прохода по 410 файлам.
2. **Обрезать и пересохранить в q=85.** Размер +4 %, PSNR ~40 dB (медиана) —
   визуально неразличимо; плитка «Записи» вырастает на треть.
3. **Обрезать и пересохранить lossless.** Новых потерь нет вообще, но
   ассеты растут с 7.8 МБ до ~22 МБ, то есть APK/AAB тяжелеет примерно на
   14 МБ.
4. **Не трогать файлы, а поменять слот плитки «Записи»** — сделать область
   фото квадратной (или ближе к квадрату) вместо нынешних 1.5:1. Тот же
   визуальный эффект без единого пересохранения, но меняет вёрстку ленты:
   плитка станет выше.

Мой выбор по умолчанию, если решать за вас: **вариант 4**, а если хочется
именно обрезки — **вариант 2**.
