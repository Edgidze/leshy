# Конвенции модуля shared

## Идентификаторы

- `namespace` = `leshy.mushrooms.map.shared`

Суффикс `.shared` существует **только в namespace**. Kotlin-пакеты внутри модуля идут
без него: `leshy.mushrooms.map.*`, а не `leshy.mushrooms.map.shared.*`. Namespace задаёт
лишь пакет генерируемого класса `R` и обязан быть уникален в пределах проекта.

## Room — схемы и миграции

- класс базы: `leshy.mushrooms.map.data.local.LeshyDatabase`
- каталог экспорта схем назван по полному имени этого класса. **При переименовании
  пакета или класса БД каталог нужно переименовать вручную** — иначе Room начнёт
  историю заново, без единой ошибки сборки
- каталог схем отслеживается git и должен оставаться в репозитории
- `.json` файлы схем **не редактировать руками** — они генерируются компилятором, ручная
  правка создаёт схему, которой никогда не существовало

### Версия 12 — базовая линия

Версия 12 будет первой опубликованной. Баз версий 1–11 вне машины разработчика
не существует и не появится, поэтому новые миграции обязаны уметь стартовать с 12,
а не с 1.

Схемы более ранних версий сохраняются для целостности истории и для цепочечного теста,
но практического значения для пользователей не имеют.

### fallbackToDestructiveMigration

Отсутствует в проекте намеренно. Не добавлять ни в каком виде, включая debug-сборки.

В релизе он не бросает исключение при ошибке миграции, а молча стирает базу — то есть
все находки пользователя, без единого сообщения. Отсутствие означает, что расхождение
схем проявится честным крашем на этапе разработки.

## Тесты миграций

Инструментальные тесты живут в source set `androidDeviceTest`, каталог схем подключён
к ним как assets.

Есть три теста:
- цепочечный v1→v12 через `runMigrationsAndValidate`
- сохранность данных для `MIGRATION_7_8`
- сохранность данных для `MIGRATION_9_10`

При добавлении новой версии БД:
1. поднять `version` в `@Database` и написать миграцию
2. собрать проект, убедиться что сгенерировался новый `.json`, закоммитить его
3. продлить цепочечный тест до новой версии
4. если миграция пересоздаёт таблицы, удаляет колонки или меняет типы — добавить
   отдельный тест на сохранность данных. `runMigrationsAndValidate` сверяет только
   схему и потерю строк не поймает

## Экспорт и бэкап

Версия формата экспорта дневника отделена от версии БД и не должна с ней связываться:
файлы экспорта переживают переустановку приложения, база — нет.

### Импорт проверяет архив ДО первой записи

`ValidateImportArchiveUseCase` прогоняется и на выборе файла (`DataViewModel.
onImportFilePicked` — пользователь узнаёт вердикт сразу, а не после ввода
приписки и нажатия «Готово»), и первой строкой самого `ImportDataUseCase.
invoke` (там отказ — `RejectedException`). Второе не дублирование: слияние
видов из архива идёт ДО разбора первой прогулки, поэтому без барьера файл,
разваливающийся на середине, всё равно оставлял бы в каталоге новые строки
категорий.

Калибровка строгости — две сознательные асимметрии:
- присутствующий, но неразбираемый `categories.json` — жёсткий отказ (иначе
  импорт молча уронил бы вид у каждой находки в `category_misc`); его
  ОТСУТСТВИЕ по-прежнему нормально, это просто архив формата v1;
- одна битая прогулка — НЕ отказ: `ImportDataUseCase` пропускает её и
  сообщает числом в `Result.failedWalkCount`, и выбрасывать девять целых
  прогулок из-за одной битой было бы хуже. Архив отклоняется, только если не
  разбирается НИ ОДНА прогулка.

### Конфликтов с уже имеющимися данными не бывает — почему именно

- **Прогулки, точки трека, отметки** вставляются с `id = 0`, Room выдаёт
  новые id. Повторный импорт того же архива даёт ещё один независимый набор
  строк, а не перезапись (тест
  `importingTheSameArchiveTwiceNeverMergesWalks`).
- **Виды** — единственное место со слиянием, по `Category.nameKey`. Ключ
  пользовательского вида генерируется как `user_<millis>_<random 6 цифр>`
  (`CreateOrUpdateUserSpeciesUseCase`), так что совпадение ключей двух РАЗНЫХ
  видов с разных устройств практически исключено по построению, а совпасть с
  каталожным ключом он не может вовсе.
- **Каталожные строки (`source == APP`) импорт не трогает ни при каких
  условиях** — явный гвард в `importCategory`. Экспорт их и не пишет, но
  `nameKey` в JSON — просто строка: правленый или битый архив, назвавший
  `boletus_edulis`, иначе прицепил бы чужую иконку каталожному виду
  (тест `importNeverTouchesCatalogSpecies`).
- **Файлы фото** именуются `imported_<millis импорта>_<исходный walkId>_<индекс>`,
  иконки видов — `catimg_<nameKey>.png` (детерминированно, чтобы повторный
  импорт перезаписывал свой же файл, а не плодил копии; локальные иконки
  живут под другим шаблоном имени, с таймстемпом).
